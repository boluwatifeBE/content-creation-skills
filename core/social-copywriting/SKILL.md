# Social Copywriting

Produces the actual, finished, copy-and-paste-ready text for a specific piece of content. Where `content-calendar` plans what to post and when, and `asset-to-content` extracts what to write about from an uploaded file, this skill is where a topic becomes finished copy in the user's confirmed voice, sized correctly for wherever it's actually going to be posted.

## Before writing

Confirm `creator-context` is active (persona, house style, philosophy, and profile). If it isn't established yet, capture the essentials first rather than writing in a generic voice.

### Draft-or-generate checkpoint (ask before writing)

Never assume the user is starting from a blank page. Ask: *"Do you already have a rough draft, some notes, or a specific opinion you want shaped into a post, or should I write this from scratch?"*

- If they have something started: work from their actual words and structure. Sharpen it, fit it to the house style and format, and fix anything that violates a hard constraint (banned words, dashes), rather than replacing their voice with a generic one.
- If they want it from scratch: proceed with the rest of this skill.
- Either way, present the result as an editable draft, invite changes rather than treating it as final.

## Carousel format (platform-independent, a fourth format alongside the three tiers)

A carousel is not bound to any platform's character limit, the text lives inside images or a PDF the user designs themselves, the platform just hosts the slides. This skill's job for a carousel is **content and per-slide visual direction**, not the actual image design, that's the user's to build.

Confirm this is what's wanted (the user says "carousel," "slides," "swipe post," or a similar request) before switching into this structure rather than the tier-based formats above.

**Structure:**
- **Slide 1, title/hook slide**: a short, punchy title or headline stating the topic, standalone enough to work as a thumbnail someone would stop scrolling for
- **Slide 2, framing slide**: a sharper headline restating or sharpening the hook, plus a short body of text that sets up why this matters, the transition from title into substance
- **Body slides (slide 3 through second-to-last)**: one distinct idea or point per slide, each short and self-contained, written to work as a standalone statement, not a fragment that only makes sense next to the slide before or after it
- **Final slide, closing**: an engagement question or clear next step, per the house style's closing-question default, but written specifically to invite a real response, a specific either/or or pick-a-side question tends to perform better than a broad open-ended one

**Slide count**: ask the user for a target count or range if not specified. Default to roughly 5 to 10 slides if not given, and say why that range fits the topic's complexity, more if the topic genuinely has that many distinct points worth their own slide, fewer if it doesn't, don't pad the count artificially.

**Per-slide visual direction (required, not optional)**: for every slide, include a short note on what visual treatment would support that slide's text, imagery direction, layout emphasis (text-heavy vs. graphic-heavy), any suggested visual metaphor or data visualization if relevant. This is genuine direction the user can hand to a designer or use themselves, not a vague "add a nice image here."

**Accompanying caption**: ask whether the user wants a separate caption to go with the carousel when it's posted, since some platforms expect slide text alone to carry the post and others expect a caption too. If yes, that caption follows the normal hashtag-behavior rules for whichever platform it's posted to (per the platform character limits above). If the carousel reads as self-contained without one, that's a legitimate choice too, let the user decide rather than assuming a caption is always needed.

**Voice and house style still apply**: each slide's text is still checked against the confirmed banlist, punctuation rule, and tone, a carousel isn't exempt from house style just because it's short per slide.

## Establishing the piece

Confirm, if not already clear from the request:

- **The topic or angle**: what is this post actually about, and what's the one real insight or lesson it delivers? A post without a specific point isn't ready to write. If the topic is vague, ask one clarifying question or propose a sharp angle and confirm before drafting, don't invent a take and present it as decided.
- **The platform(s)**: pull from the user's actual platform list in `creator-context`. If the user wants the same post/topic published across multiple platforms at once (common, and the default `content-calendar` now plans for), treat this as one core idea adapted per platform, not the same fixed text force-fit everywhere, see **Platform Character Limits** below for exactly how each platform's version needs to differ.

## Platform character limits (check every draft against these)

These are real, hard platform constraints, not house-style choices, so they apply regardless of what the user's formatting preferences are. Know the limit for the platform being written for before drafting, not after.

| Platform | Limit | Tier |
|---|---|---|
| X | 280 characters | Short-form |
| Threads (post) | 500 characters | Short-form |
| Threads (topic tag) | 50 characters | Short-form |
| Instagram / TikTok (Story caption) | 120 characters | Short-form |
| Instagram / TikTok (main post caption) | 2,200 characters (roughly 300 to 400 words) | Platform-native long post |
| Facebook (post / reel caption) | 5,000 characters | Platform-native long post |
| LinkedIn Standard Post | 3,000 characters | Platform-native long post |
| LinkedIn Article | No practical limit | True long-form article |
| Medium | No practical limit | True long-form article |
| Substack | No practical limit | True long-form article |
| Custom platform | Ask the user for its actual limit if not already captured in `creator-context`, don't assume | Whichever tier the limit and use case actually match |

**Critical distinction**: a LinkedIn Standard Post and a LinkedIn Article are not the same format, even though they're the same platform. A Standard Post is capped at 3,000 characters, closer to Facebook or an Instagram caption in scale than to a true article. If a long-form piece is actually meant to run on LinkedIn as a Standard Post, it needs to fit in 3,000 characters, it cannot just be written like a Medium article and dropped in, that's what caused the piece to not fit in a previous session. If the user wants the fuller, unbounded version, that's a LinkedIn Article, a different format, confirm which one they actually mean before writing.

## Format specs by tier

**Short-form (X, Threads posts/topics, Story captions)**
- Hook line first: names the real problem or tension in one line, no throat-clearing
- Extremely tight, every word has to earn its place at this length
- A closing question, if there's room, is a nice-to-have here, not a requirement, don't sacrifice the actual point to fit one in
- Must fit the platform's exact character limit, count before presenting

**Platform-native long post (Instagram/TikTok main caption, Facebook, LinkedIn Standard Post)**
- Still written in short-form *style* even though the character allowance is generous, hook first, short paragraphs (1 to 3 sentences), builds the insight rather than describing it. The extra room is for depth of thought, not for switching into essay structure or subheadings.
- Closes with an introspective question by default, per the house style's formatting model, unless a deviation has been proposed and agreed
- Must fit the platform's specific limit (2,200 / 5,000 / 3,000 characters respectively), count before presenting. If the draft is a genuinely long-form idea that won't fit even after tightening, say so directly and ask whether to trim it down to fit this format, or whether the piece actually belongs in the true long-form article tier instead (see below)

**True long-form article (LinkedIn Article, Medium, Substack)**
- Same hook-first opening, but full room to develop the idea with a real arc: the problem, why it's actually happening, what the shift in thinking looks like, what to do about it
- Subheadings once the piece is long enough to need them (roughly 600+ words), don't force structure onto a shorter piece
- Bullets only for genuinely sequential or tactical content, not as an organizing crutch
- Closes the same way by default: an introspective question, not a generic CTA
- No hard cap, let the idea determine length, but don't pad. If the user gave a word count, hit it.

## Length check before presenting (required)

Before presenting any draft, check its actual character count against the specific platform's limit from the table above. If it doesn't fit:
- For short-form or platform-native long post tiers: trim it down, cutting weaker material rather than proportionally shortening every sentence, same discipline `content-repurposing` uses for compression.
- If trimming would genuinely gut the piece's substance, say so and ask whether the user wants it trimmed anyway, or whether this piece actually belongs in the true long-form article tier and should be redirected there instead of forced into a shorter format.
- Never present a draft that's over the platform's actual limit without flagging it, the user shouldn't discover a piece doesn't fit only after trying to post it.

## Carousel format (platform-agnostic, slide-based)

A carousel is a different shape of content entirely, not a length tier. It's posted as a sequence of images or a PDF, so it isn't bound by any platform's character limit, the constraint here is legibility per slide and how many slides the topic actually needs, not a text-length cap. This skill provides the content and a visual direction note for each slide, the user designs the actual images themselves.

**Structure**:
- **Slide 1, hook**: the single most attention-grabbing framing of the whole topic, title only, little to no body text. This is what decides whether someone keeps swiping.
- **Slide 2, context/setup**: a short headline plus one to three sentences establishing why this topic matters now or what problem it addresses.
- **Body slides (3 through the second-to-last)**: one specific point, insight, or step per slide, one to three sentences each. Don't split a single idea across two slides, and don't cram two ideas onto one, each slide should be a complete, standalone thought.
- **Final slide, closing**: a specific, genuine question tied to the actual content, per the house style's formatting model, never a generic "let me know in the comments." This is the one place a carousel should explicitly invite discussion.

**Slide count**: driven entirely by how many points the topic genuinely supports, don't pad to hit a round number, and don't cram the topic down to an artificially short count either. A topic with three real points and one forced into padding is worse than a shorter carousel that ends when the substance does.

**Visual direction per slide**: alongside each slide's text, include a short, concrete suggestion for what visual treatment would pair with it, a color shift, an icon, a photo type, a chart, whatever fits that specific slide's content. This is lighter than a full visual design spec, the user is doing the actual design, this is direction, not a mockup.

**The accompanying caption**: a carousel still needs a caption when it's actually posted, and that caption *is* platform-specific, follow the normal short-form or platform-native long post rules and character limit for whichever platform it's going to, per the tables above. Only the slide content itself is platform-agnostic, the caption is not.

**Voice and house style** apply per slide exactly as they do everywhere else in this system, banlist, punctuation rule, tone, checked before presenting.



The formatting model above is the house default, not a rigid requirement for every piece. If a specific piece would genuinely read better without part of it, a reflective essay that doesn't want a closing question, a technical breakdown that doesn't want a punchy hook, propose that deviation explicitly and say why, then proceed based on the user's answer. Don't silently deviate, and don't force the default where it clearly doesn't serve the piece.

## Voice enforcement

Every draft must be checked against the house style confirmed in `creator-context` before it's presented as finished: the confirmed tone, the confirmed punctuation rule, the confirmed banlist (default or user-modified), and the confirmed formatting model (or an agreed deviation). If a first draft violates any of these, rewrite the offending sentence rather than delivering it with a note, the user shouldn't have to edit out a banned word or a stray dash themselves.

## Writing the same topic across multiple platforms

When a topic is meant to run across several platforms at once (per a multi-platform `content-calendar` entry, or a direct request), treat it as one core idea, not one fixed piece of text copy-pasted everywhere. Adapt depth and structure to each platform's actual tier and limit: the X version and the LinkedIn Standard Post version of the same idea will genuinely differ in how much room they have to make the point, not just in length. Present each platform's version separately and clearly labeled, each one individually checked against its own limit.

## Working from a content-calendar entry

If the user references a calendar entry ("draft the Tuesday LinkedIn post" or similar), pull the pillar, hook, and angle already established for that slot rather than starting from scratch, expand it into the full format above, at the correct tier for whichever platform(s) that entry targets.

## Presenting the draft

Present the finished copy as plain text, ready to copy and paste, not inside a code block. Label which platform each version is written for, and note the character count relative to that platform's limit (e.g. "247/280 characters") so the user can see it fits at a glance. If the user wants to see how it would look on the platform itself, that's a visual concern, hand off to `visual-direction` if that skill is active, otherwise just note that a visual pairing is worth considering.

**For a carousel**, present each slide clearly numbered and separated, slide text first, then its visual direction note immediately beneath it, so the user can move slide by slide into whatever design tool they're using without having to cross-reference two separate lists.

If the user wants revisions, edit the existing draft rather than regenerating from scratch, unless they ask for a completely different angle.
